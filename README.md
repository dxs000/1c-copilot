# 1С Project Copilot

Аналитическая RAG-система для проектов на 1С на Yandex Cloud AI Studio. Один индекс связывает
проектную переписку, ТЗ, допсоглашения и ПиМИ с метаданными и BSL-кодом конфигураций (.cf),
расширений (.cfe) и внешних обработок (.epf). Концепт — в проекте RAG8: «Концепт аналитической
RAG-системы для 1С на Yandex Cloud AI».

## Что уже есть (фаза 1: документы и почта + разбор кода)

### Форматы

| Формат | Как разбирается |
| --- | --- |
| .msg, .eml | Письмо + **цитируемые хвосты режутся на отдельные письма** (From/Sent/To/Subject Outlook RU/EN, «… пишет:», Gmail); вложения рекурсивно, msg в msg |
| .docx | Заголовки по outlineLvl, стилям и многоуровневой автонумерации (номера восстанавливаются); оглавление пропускается; зачёркнутый текст — отдельно как удалённые формулировки; комментарии рецензентов с фрагментом |
| .pdf | Текст вне таблиц, таблицы с переносом через страницы, заголовки по нумерации; сканы — через OCR |
| .xlsx | Листы как таблицы с объединёнными ячейками (матрицы тестов, реестры) |
| .doc, .xls, .rtf, .odt, .ppt(x) | Конвертация LibreOffice → docx/xlsx/pdf |
| .zip | Рекурсивно, имена в cp866 из Windows-архивов |
| .png, .jpg | Yandex Vision OCR (в облаке) или tesseract с rus (локально); картинки меньше 20 КБ — логотипы, пропускаются |

### Что извлекается из таблиц

| Таблица | Распознаётся по шапке | Куда идёт |
| --- | --- | --- |
| Тест-кейсы ПиМИ | № · Функция · Методика · Критерий · Результат | `test_cases`: кейс со всеми шагами (строки с одинаковым №), итог — худший результат шагов |
| План тестирования ТЗ | № · Наименование объекта · Процедура проверки | `requirements`: пункт плана с группой («3. НСИ») и всеми процедурами |
| Покрытие | Документ · Пункты плана тестирования · Покрытие | `requirement_tests`: какие ПиМИ покрывают какие пункты («1–9, 129, 147–151» раскрывается) |
| Прочие | — | Чанки «заголовок: значение» с группами из объединённых строк |

Из этого SQL сразу отвечает, например, «какие пункты плана ТЗ не покрыты ни одним ПиМИ» (`uncovered_requirements`).

### Дедупликация корпуса

Одно письмо приходит файлом, вложением и цитатой; один документ — файлом, вложениями в несколько
писем и подписанным PDF. В индекс каждое попадает один раз (письмо — по отправителю и минуте
отправки или по началу текста; документ — по содержимому или по типу/версии/названию для docx↔PDF),
остальные появления сохраняются: у документа — «получен: вложение письма «…» от дд.мм.гггг, отправитель».

## Быстрый старт

```bash
uv sync --extra dev
uv run pytest

# Локально, без облака: посмотреть, как режутся ваши материалы
uv run copilot1c parse-docs path/to/mails path/to/docs --report   # сводка: письма, документы, реестры, пропуски
uv run copilot1c parse-docs path/to/mails path/to/docs            # все чанки
uv run copilot1c entities path/to/mails
uv run copilot1c parse-code path/to/dump --config "УТ 11.5.27.75"
```

С облаком: скопируйте `.env.example` в `.env`, заполните каталог и API-ключ AI Studio, затем

```bash
uv run copilot1c init-db                    # схема; нужен PostgreSQL с pgvector
uv run copilot1c index-docs data/mails data/docs --llm-entities
uv run copilot1c search "с какой версии обновляется УТ"   # что найдёт поиск: место в векторном и лексическом списках
uv run copilot1c ask "Почему обновляемся на 11.5.27.75, а не на 11.6?"
```

### Поиск

База поиска — таблица `chunks` в PostgreSQL (`search.py`). Эмбеддинги считает AI Studio (модель документов
при записи, модель запросов при поиске), ищет PostgreSQL: векторная близость (pgvector, точный перебор) и
полнотекстовый поиск с русской морфологией, списки сливаются по RRF. Номера версий («11.5.19.55») словарь
хранит целиком — они находятся точно. Фрагмент несёт статус (`active` / `superseded` — заменён новой
редакцией, в поиск по умолчанию не попадает), контуры и материал, из которого пришёл.

AI Studio Vector Store больше не используется: там один фрагмент — один файл при лимите 10 000 файлов на
индекс, удаление и редакции пришлось бы синхронизировать отдельно.

- `copilot1c contours` — справочник контуров; `--add system:"УТ 11" --aliases "УТ11,Управление торговлей"`.
- `copilot1c reset-knowledge --yes` — очистить фрагменты, граф, реестры и реестр загрузок (обращения,
  контакты и контуры остаются).
- `DELETE /materials/{id}` — убрать материал из базы поиска.

### «Входящие»: разбор и приём

Аналитик сам приносит материалы: в чат («+») или на экран «Входящие». `POST /intake/analyze` ничего не
сохраняет и по каждому файлу отвечает:

- что это: вид (ТЗ, бизнес-требования, AS-IS / TO-BE, протокол, инструкция…), название, редакция, о чём;
- к чему относится: контуры справочника — по названиям и псевдонимам в тексте, моделью (`COPILOT_INTAKE_LLM`)
  — выбор из справочника или предложение нового контура;
- что уже в базе: этот файл уже загружали; то же содержание (отпечаток без названия — имя файла не важно);
  похоже на новую редакцию документа «…»; для писем — ветка, новые и известные письма; вложения письма,
  приложенные и отдельно;
- предложение: добавить, новая редакция, сохранить без индексации, не добавлять.

`POST /intake/accept` — файлы с решениями аналитика (действие, контуры, документ для новой редакции, новые
контуры) в реестр материалов; обработчик индексирует их с контурами, ведёт документы и редакции: новая
редакция становится текущей, фрагменты прежней — `superseded`. `DELETE /materials/{id}` забывает и
редакции (текущей снова становится предыдущая), и письма материала. В чате сообщение «просмотри документы,
добавь в хранилище» — тип `intake`: агент получает разбор приложенного и задачу, ответ — с карточкой приёма.

### Система и подсистема обращения

У обращения — система и функциональный блок из справочника контуров («УТ 11 › Продажи», «Инфраструктура ›
Терминальные серверы»). Стартовый справочник (УТ 11, БП 3.0, ЗУП 3, инфраструктура) заводит `init-db`, если
справочник пуст (`copilot1c contours --seed` — дополнить). Дальше он растёт по ходу работы: новый блок
заводится из карточки обращения, модель предлагает пункт, если подходящего нет.

Предложение (`POST /issues/suggest-contours`, `contours.suggest`): объект 1С из текста ошибки → подсистема
(точнее всего), слова и псевдонимы контуров (с учётом окончаний), модель — в спорных случаях. Когда аналитик
относит обращение к блоку, объекты 1С из него становятся псевдонимами блока. Статус «передано» с полем «кому» —
для обращений не по профилю. Список фильтруется по системе вместе с её блоками; похожие обращения из другой
системы весят меньше; разбор решённого обращения уходит в базу с контурами обращения. Для заведённых раньше —
`copilot1c suggest-issue-contours` (показать) и `--apply` (записать).

### Письмо по обращениям

Аналитик бросает .msg в чат одной фразой («просмотри; при необходимости зарегистрируй новое обращение или обнови
существующее») — тип сообщения `issue_mail`. Разбор (`POST /issues/triage`, `mail_triage.py`) находит
обращение по признакам: ветка переписки уже связана с обращением; тот же файл или Message-ID — источник
обращения; номер ОБР в вопросе или письме; номер заявки из темы (`0000026095`, `INC…`, `[#…]`) в
`issues.external_refs`; похожий текст — только кандидат. Предлагает «обновить ОБР-…» (новые письма, что
изменилось, комментарий в историю, статус — моделью или шаблоном), «новое обращение» или «только в базу».

Письмо, прикреплённое к обращению, записывается в ветки, ветка связывается с обращением, номера заявок из
темы — в обращение: следующий ответ по той же переписке узнаётся сам. Каждое письмо ветки — отдельный пункт
истории обращения (тип `letter`): автор, роль (сотрудник, аналитик, внешний исполнитель, уведомление системы
заявок), время отправки, текст без цитат; история упорядочена по времени событий, повторно письмо не попадает. Для обращений, заведённых раньше, —
один раз `copilot1c link-issue-emails`.

### Письма и ветки

Каждый ответ в переписке несёт небольшое обновление и весь хвост в цитатах. Поэтому письма хранятся по
одному (`letters`), связанные в ветки (`threads`):

- письмо из файла сверяется с известными: по Message-ID, иначе по отправителю, времени (окно ±14 ч —
  время в заголовке цитаты без пояса; «та же минута с точностью до пояса» снижает порог) и тексту (шинглы,
  доля общих от меньшего — цитату Outlook обрезает); известное в базу поиска повторно не идёт;
- строки, вписанные внутрь цитаты («ответы ниже красным»), приписываются автору верхнего письма;
- ветка — по пересечению с известными письмами, а не по теме; совпали письма двух веток — ветки сливаются;
  иначе — ветка с той же темой и общим участником за 90 дней, иначе новая;
- сводка ветки (суть, сделано, ждём, статус, открытые вопросы) пересобирается при новых письмах — моделью
  `COPILOT_MODEL_BATCH` (`COPILOT_THREAD_SUMMARY_LLM=false` — шаблоном) — и лежит фрагментом в базе поиска;
- письмо, приложенное к вопросу в чате, агент видит как сводку ветки + только новые письма; инструмент
  `get_thread` — вся ветка; вложение письма, приложенное и отдельным файлом, второй раз не разбирается.

Методы: `POST /letters/check` (пробный прогон, ничего не пишет), `GET /threads`, `GET|PATCH /threads/{id}`,
`POST /threads/{id}/summary`.

Распаковка кода — на ВМ с платформой 1С 8.3.27 (путь к `1cv8` в `.env`):

```bash
uv run copilot1c unpack data/cf/UT11.cf data/dumps/ut11-5-27-75
uv run copilot1c unpack data/cfe/KS.cfe data/dumps/ks --extension КС_Доработки
```

## Демон ядра

`copilot1c serve` поднимает HTTP API ядра только на `127.0.0.1:8100` — для веба, бота и MCP.
Секреты (`.env`) и состояние (`.cache`: кэш OCR, журналы) остаются у демона.

```bash
uv sync --extra server
uv run copilot1c serve
curl -s http://127.0.0.1:8100/health   # AI Studio, база поиска, PostgreSQL, платформа 1С
```

На хосте — служба systemd `deploy/copilot1c-core.service` (пользователь `copilot`, каталог `/opt/1c-copilot`):

```bash
sudo cp deploy/copilot1c-core.service /etc/systemd/system/   # и после каждого его изменения
sudo systemctl daemon-reload
sudo systemctl enable --now copilot1c-core
journalctl -u copilot1c-core -f
```

Служба работает в песочнице (`ProtectSystem=strict`): писать можно только в `.cache`, `data` и `issues`
(вложения обращений) — список `ReadWritePaths` в файле службы. Папка, в которую ядро начинает писать,
добавляется туда же; `GET /health` показывает, доступна ли папка вложений (`checks.issues_files`).

### Обращения

Проблемы, о которых сообщают аналитики интегратора, ведутся в PostgreSQL (`issues.py`):
`issues` — обращения (суть, классификация, статус, окружение, инициатор, связи, итог, `version`
против одновременной правки), `contacts` — инициаторы (сотрудники заказчика, уникальны по e-mail),
`issue_attachments` — вложения (файлы в `issues/<id>/`, вне `data` — в индекс не попадают),
`issue_events` — история: создание, правка каждого поля, смена статуса, комментарии, вложения.

Методы демона: `GET /issues/meta`, `GET|POST /issues`, `GET|PATCH /issues/{id}`,
`POST /issues/{id}/comments`, `POST /issues/{id}/attachments`, `GET /issues/{id}/attachments/{aid}`,
`GET|POST /contacts`, `POST /classify`, `GET /issues/{id}/related`, `POST /issues/related`, `POST /issues/{id}/kb-draft`, `POST /issues/{id}/kb-publish`. Список аналитиков — `COPILOT_ANALYSTS` в `.env` (JSON-список).
После обновления ядра таблицы создаются командой `copilot1c init-db` (существующие данные не трогаются).

Тип сообщения в чате (`intent.py`): `POST /ask` кроме ответа агента возвращает `intent` — вопрос,
проблема, сводка, документ или новое знание (с баллами и сигналами, почему так) — и `issue_draft`,
если это сообщение о проблеме: тема, описание, текст ошибки 1С, объекты, категория, приоритет.
Решают эвристики; спорные случаи — модель (`COPILOT_INTENT_LLM`). `POST /classify` — то же без агента.
`POST /ask/files` — вопрос с приложенными файлами («+» в чате): их текст идёт агенту контекстом этого вопроса
(в базу не сохраняется); для письма о проблеме черновик обращения получает инициатора, дату и Message-ID.

Интернет для агента (`web.py`): инструменты `web_search` и `read_page` — только если в базе проекта ответа нет,
и вопрос про платформу, типовую конфигурацию, ошибку или версию. Запрос очищается в коде: имена, e-mail,
телефоны, серверы, внутренние адреса и сети, свои домены, `COPILOT_WEB_BLOCKED_TERMS` не уходят; журнал —
`.cache/web/web_search.jsonl`; лимиты на вопрос — `COPILOT_WEB_MAX_SEARCHES`, `COPILOT_WEB_MAX_PAGES`.
`read_page` открывает только внешние страницы (внутренние адреса и редиректы туда отклоняются). В ответе `/ask` —
`web_sources`. Проверка с хоста: `copilot1c web-search "текст" --site its.1c.ru --read`.

Эксперт через оператора (`escalate.py`): если ответа нет в базе и в интернете или нужна глубокая работа, агент
вызывает `prepare_escalation` (причина + вопрос эксперту) — в ответе `/ask` поле `escalation`. Аналитик собирает
пакет: `POST /escalations` (вопрос, ответ агента, фрагменты, ссылки, приложенные файлы или `issue_id`) →
`.cache/escalations/<id>.zip` с `PROMPT.md`, `materials/*.md`, `MANIFEST.json`; `GET /escalations/{id}` — скачать.
Имена (инициатор, аналитики, авторы писем), e-mail и телефоны в текстах пакета убраны; исходные файлы — только по
явному разрешению (`include_raw`).

База знаний из решённых обращений (`kb.py`): `kb-draft` готовит разбор «симптом → причина → решение»
(модель `COPILOT_MODEL_BUSINESS_TEXT` по полям обращения или шаблон; без имён, e-mail и телефонов),
`kb-publish` сохраняет его материалом «Решение ОБР-… — тема.md» — дальше обычный конвейер «Материалов».

Разбор письма в обращение (`email_intake.py`, `POST /issues/from-email`): из .msg/.eml собирается
вся цепочка (само письмо, цитаты, письма-вложения), инициатор — последний автор из своих доменов
(`COPILOT_INTERNAL_DOMAINS`), который не аналитик (`COPILOT_ANALYST_EMAILS`, запасным путём — фамилии
из `COPILOT_ANALYSTS`). Должность, телефон и организация — из подписи (эвристика). Черновик не
сохраняется: аналитик проверяет его в карточке. Повторная регистрация того же письма отсекается по
Message-ID письма пользователя или отпечатку «адрес + время + тема». `POST /issues/{id}/attachments`
с `expand=true` прикрепляет письмо вместе со вложенными в него файлами (логотипы подписей отбрасываются).

## Оценка качества

Перед расширением (код 1С, генерация) качество поиска и ответов меряется на эталонных вопросах:

```bash
uv run copilot1c eval data/eval/ut11-golden.json            # только поиск: recall@10
uv run copilot1c eval data/eval/ut11-golden.json --answers  # плюс ответы агента: обязательные факты
```

Формат набора — `tests/eval/example.json`: вопрос, фрагмент-доказательство, который должен найтись в
top-k, и факты, которые обязаны быть в ответе. Наборы по реальным проектам держите в `data/eval/`
(не коммитится: репозиторий публичный). Подробный отчёт сохраняется в `.cache/eval/`.
Цель MVP по концепту — recall@10 ≥ 0,85.
